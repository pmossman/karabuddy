# 0003 — Local dev DB isolation via Docker Postgres

**Status:** Accepted (B74, 2026-05-30). Live.

## Context

`.env.local` is generated by `vercel env pull` and carries the **production**
Neon connection (every Vercel env shares one Neon DB). So local dev ran against
prod data: a stray local `db:migrate`, a test write, or a destructive-flow test
hit production. This actually happened — B71's `0010` migration had to be
applied to prod just to unblock localhost.

## Decision

- Run local against a **local Docker Postgres** (`docker-compose.dev.yml`,
  `postgres:17` to match prod's PG17, host port `5434` — the test DB is a
  separate ephemeral container on 5433).
- Use the app's existing `KARABUDDY_DB_DRIVER=pg` path (node-postgres) — no app
  code change.
- Put local overrides in **`.env.development.local`** (gitignored): it loads at
  higher precedence than `.env.local` in both Next.js and `drizzle.config.ts`,
  and `vercel env pull` never touches it. So the local DB override wins and
  survives an env re-pull.
- Keep `.env.local` as the prod **snapshot source**: `db:pull-snapshot`
  (`scripts/pull-prod-snapshot.sh`) runs `pg_dump | pg_restore` inside the
  container, reading prod read-only and always restoring into local. It refuses
  a local-looking source so it can't run backwards onto prod. Blob payloads
  aren't copied — `payloadBlobUrl` keeps pointing at prod Blob (read-only).

## Consequences

- First-time setup adds a Docker step (see `docs/local-dev-db.md`).
- The snapshot includes real PII (emails, tokens) — same exposure as before;
  the Docker volume is local, don't commit dumps.
- Migration/backfill scripts target whatever the env points at — for a
  deliberate prod run, pass prod creds explicitly. Confirm `db:migrate` reports
  `localhost:5434` before running it locally.
- Sibling to [0002](./0002-gated-deploys.md): same root cause (shared Neon DB),
  different surface (local vs CI/preview).
