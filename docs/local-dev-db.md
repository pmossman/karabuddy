# Local dev database (B74)

Local dev must NOT run against production. Out of the box `.env.local` is
generated by `vercel env pull` and carries the **prod** Neon connection —
which is how a local `db:migrate` ended up mutating prod and why a missing
local table showed up as prod-shaped 500s. The fix: run local against a
**local Docker Postgres**, seeded from a prod snapshot.

The app already supports this — `KARABUDDY_DB_DRIVER=pg` (see `lib/db.ts`)
swaps the Neon HTTP driver for node-postgres against any plain Postgres.

## How it's wired

- **`docker-compose.dev.yml`** — a persistent Postgres on host port `5434`
  (the test DB uses 5433 and is ephemeral; these don't clash).
- **`.env.development.local`** (gitignored) — local overrides that
  `next dev` loads at HIGHER precedence than `.env.local`, and that
  `vercel env pull` never touches:
  `KARABUDDY_DB_DRIVER=pg` + `POSTGRES_URL`/`POSTGRES_URL_NON_POOLING`
  pointing at the Docker DB.
- **`drizzle.config.ts`** loads `.env.development.local` first, so
  `db:migrate` targets the local DB too.
- **`.env.local`** stays prod (Vercel-managed) — it's the snapshot *source*.

## First-time setup

1. Launch **Docker Desktop** (so the `docker` CLI + daemon are available).
2. `npm run db:dev:up` — start the local Postgres.
3. `npm run db:pull-snapshot` — dump prod (read-only) and restore it into
   the local DB. (Runs `pg_dump | pg_restore` *inside* the postgres:17
   container, so you need no host Postgres tools. `-- --yes` skips the
   prompt.) This also brings the schema, so a separate `db:migrate` is a
   no-op — though `npm run db:migrate` is the command if you ever start from
   an empty DB instead of a snapshot.
4. Restart `npm run dev`. Local now reads/writes the Docker DB; prod is
   untouched. Verify the target is local (not prod) — `drizzle-kit` doesn't
   print the host, so check the resolved URL directly:
   `node -r dotenv/config -e 'console.log(process.env.POSTGRES_URL_NON_POOLING)' dotenv_config_path=.env.development.local`
   should print a `localhost:5434` URL. Then confirm the team page loads.

## Refreshing / teardown

- Re-pull prod data anytime: `npm run db:pull-snapshot`.
- Stop the DB (data persists in the volume): `npm run db:dev:down`.
- Wipe it completely: `docker compose -f docker-compose.dev.yml down -v`.

## Notes

- **Blob payloads aren't copied.** `replays.payloadBlobUrl` keeps pointing
  at prod Vercel Blob URLs, which load read-only from local — so replays
  play back without copying gigabytes.
- **PII:** the snapshot includes real user rows (emails, install/extension
  tokens) — same data you had when local pointed at prod. The Docker volume
  is local; don't commit dumps.
- **Direction is enforced:** the snapshot reads prod from `.env.local` and
  always restores into the local container; it refuses if the source looks
  local, so it can't run backwards onto prod.

## Relation to previews (B72)

Same root cause as B72's preview-DB isolation — every Vercel environment
(Production/Preview/Development) currently shares one Neon DB. This doc
covers the *local* surface; the Neon–Vercel integration's per-preview
branching covers Vercel previews.
